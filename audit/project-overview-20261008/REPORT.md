## 1. 结论与边界

Android 手机端已经具备较完整的媒体客户端功能：多服务器、首页与媒体库、搜索与详情、播放与字幕、下载、同步、投屏、一起看、日历、账户与更新均有实际实现；电视端共享核心能力并提供遥控操作入口。不能把这些模块简单归为“未完成”。

当前最需要投入的是实际运行证据、跨模块一致性和维护成本。本次 Android/协议/服务端主机测试共执行 **3,970 项，全部通过**，接收器与日历渲染调度的 Node 测试 **10 项通过**。这些结果支持逻辑层的稳定性，但不等价于真机 UI、硬件解码、音频输出、投屏接收端或生产服务验收。

HarmonyOS 当前属于移植阶段。能力清单中的 32 项没有任何一项达到其定义的 `implemented`：4 项源码接通、14 项仅逻辑、7 项缺 SDK 适配、3 项占位界面、3 项受能力门控限制、1 项只有契约。本机可编译 8 个逻辑包并通过 33 项测试；另外 4 个包缺少 stdx 依赖。缺少完整 HAP 构建与设备运行证据，不能据此宣布 Harmony 版本可交付。

本次未在通过的主机测试中发现新的 P0 功能故障。下文 P0 表示相应发布或能力推广前必须满足的验收条件；P1 表示应优先修复的检查缺陷或补齐的重要可靠性证据；P2 表示后续结构、体验与能力一致性优化；P3 表示按产品需求安排的扩展。对性能、容量和平台适配的判断，均明确区分已确认限制与待测风险。

## 4. 重点问题及证据

### F01：Harmony CI 没有覆盖当前主分支的直接提交（确认，P1）

[harmony-source-gates.yml](D:/Demo/Yfuse/.github/workflows/harmony-source-gates.yml:5) 的 push 分支仅为 `feature/harmony-cangjie`，而当前工程位于 `master`。符合路径的 PR 会运行检查，但直接向 master 提交 Harmony 相关修改不会触发该工作流。push 和 pull_request 的路径列表也遗漏了 `scripts/verify-cangjie-host.py`，仅修改该文件时不能依靠该工作流验证。

影响：检查覆盖不完整，验证器自身改动也可能缺少自动验证。应补齐主分支及验证脚本路径，并以实际工作流触发记录验收。

### F02：Harmony 主机验证把部分完成报告为总体 PASS（确认，P1）

[verify-cangjie-host.py](D:/Demo/Yfuse/scripts/verify-cangjie-host.py:111) 没有编译器时输出 SKIP 并返回 0；存在 stdx 阻塞包且其余项目没有失败时，仍在末尾输出 `PASS Cangjie host verification`。本机实际就是 8 包编译成功、4 包 BLOCKED、33 项测试通过的部分完成状态。当前 CI 未配置 Cangjie SDK，纯源码门控不等于 SDK 构建检查。

影响：调用者若只读退出码/最后一行，容易高估覆盖范围。应让验证记录区分完整通过、部分通过、跳过、阻塞和失败，并在要求 SDK 验证的检查中拒绝缺失结果。现有未签名发布门控保持关闭；没有证据表明这个标记问题已绕过发布签名门控。

### F03：新版 Android 与媒体能力缺少本次真机证据（验证缺口；对应发布前 P0）

手机与 TV 已声明局域网权限，并有运行时授权路径，不能判为“漏配权限”。但 target 37 对局域网访问的运行时权限要求，需要在相应版本上实测拒绝、撤销、恢复与不同入口。官方规则见 [Android 局域网权限](https://developer.android.com/privacy-and-security/local-network-permission)。

本轮详情手势与可预测返回修复通过回归测试；现有 Android 9/API 28 设备无法验证 Android 14+ 可预测返回，也无法代替 API 37 权限验收。播放、PiP、后台、投屏和 TV 输出同样有硬件与系统差异。native-only 运行时不是当前默认配置；其推广必须沿用现有专项设备、跳转/Surface 与长时门控，不能仅凭单元测试升级能力声明。

### F04：房间生命周期和服务容量有明确边界（限制/待测风险，P1）

[WatchRoomStore.kt](D:/Demo/Yfuse/watchTogetherServer/src/main/kotlin/com/yfuse/watch/WatchRoomStore.kt:35) 使用进程内 `ConcurrentHashMap` 保存房间，因此服务重启后房间状态无法从该存储恢复。多实例部署需保证房间归属及通信路由。先明确产品是否要求房间跨重启恢复，再决定排空/重建、粘性路由或共享状态方案。

[AccountStore.kt](D:/Demo/Yfuse/watchTogetherServer/src/main/kotlin/com/yfuse/watch/account/AccountStore.kt:140) 用单连接锁串行访问，且采用 busy_timeout、WAL、FULL 同步策略；这些配置已有可靠性考虑。高并发下的等待时间和吞吐仍需测量。已有备份脚本不等于恢复演练通过，本轮未发现或声称数据库损坏。

### F05：详情预热可能被进度变化重建（源码可推导风险，P1 先测量）

[DetailComponent.kt](D:/Demo/Yfuse/composeApp/src/commonMain/kotlin/com/yfuse/feature/detail/DetailComponent.kt:458) 的预热键包含 `startPositionTicks`，键变化后会释放旧预热并创建新任务。同步进度更新可能因此增加准备开销。尚无本次 trace 证明发生频率或对首帧的影响。

完整剧集队列与备选来源已经延迟到播放器接管并出现首帧之后，不能再以旧审计中的“进入详情就拉全队列”作为当前缺陷。若测量证实有重建成本，再拆分媒体身份与起播位置，在接管时重新应用最新位置，并验证版本/服务器切换及续播准确性。

### F06：核心文件规模增加修改和回归成本（确认规模，P2）

共享 Kotlin 生产源码约 964 个文件、239,305 行。播放器、原生/增强调度、下载、更新等多个文件超过 2,000 行；`PlayerRoot.kt` 约 3,991 行，`AndroidNativeDirectYPlayer.kt` 约 3,686 行。服务端日历采集与路由入口也较大。

这是结构性维护风险，不代表这些功能现在不可用。应先定义稳定行为边界，再小步拆分状态、输出策略、生命周期、副作用与 UI；避免一次性重写多引擎体系。

### F07：验证环境依赖与功能完成度表达需要统一（确认，P1/P2）

本机脚本测试缺 jq，Harmony 总检查缺 PyYAML；另有 Cangjie stdx 缺失。这些是当前验证阻塞，不能直接当作业务功能失败。CI 已固定 PyYAML 6.0.3，不存在本报告声称的未锁定依赖问题。

跨端/跨服务器能力也有明确差异：元数据与图片镜像关闭、Plex 部分能力不可用、手机仅 arm64、Harmony 有占位与门控功能。应让界面、能力清单、版本说明与真实验收状态保持一致。历史性能和移植文档可作为线索，但不能自动继承为当前提交的测量结果或当前仍未修复的问题。

## 5. 可执行优化计划

验收必须绑定测试提交、运行配置、设备/服务版本和产物身份。下面的预期效果是优化目的，不是已经测得的改善幅度。执行人可按移动端、媒体内核、服务端与构建职责分工，不在缺少资源信息时承诺日历日期。

### T01 · P0：补齐 Android/TV 系统与手势发布验收

- **目标与责任**：移动端/TV 负责人确认系统行为和返回操作符合预期；对应版本发布前完成。
- **具体改进**：在 Android 14+ 与 API 37 设备运行详情滚动、斜向/快速滑动、多指、子容器滚动、返回开始后切换页面/关再开覆盖层、播放器切后台、旋转、PiP、IME 与大屏用例；保留最低支持版本和 TV 遥控返回检查。局域网覆盖首拒、撤销、重新授权、手动 IP、私有 DNS、IPv6、发现/投屏/SMB 入口。
- **验收与效果**：误触手势、取消手势均不退出；一次提交只返回一次；所有返回路径状态恢复；拒绝权限有可恢复提示，重新授权无需重装；保存设备矩阵、日志与录屏。消除逻辑通过但系统行为未验证的发布盲区。
- **依赖**：相应系统设备/模拟环境，真实 TV；现有手势回归测试必须保持通过。

### T02 · 条件 P0：完成原生媒体运行时推广证据

- **目标与责任**：媒体内核负责人在推广 native-only 或新增高级输出声明前证明实际输出和长时稳定性。
- **具体改进**：沿用现有原生发布标准：18 案例、4 台真机、至少 3 类 SoC；完成 1,000 次验证过的 seek、1,000 次 Surface 生命周期、8 小时连续播放及 24 小时队列稳定性，队列包含至少 100 次真实下一项切换。覆盖 HDR/DV、音频、字幕/光盘和引擎回退。
- **验收与效果**：数值证据与提交、AAR、APK 哈希匹配；高级输出有真实设备确认；不支持能力继续保持门控。提高能力声明可信度，降低新运行时推广风险。
- **依赖**：专项设备与素材、既有原生检查工具。此任务不表示当前默认 full 配置已改为 native-only，也不要求所有普通改动重复全套推广检查。

### T03 · P1：建立跨模块关键用户旅程验收

- **目标与责任**：移动端/TV/服务端联合验证真实业务闭环。
- **具体改进**：以 Emby、Jellyfin、Plex 实际环境测试“登录→列表/搜索→详情选源→播放→续播→下载/离线→同步”；联测 Cast/DLNA、一起看重连、手机接力/遥控及真实 Trakt 授权上报；加入服务器切换、过期凭据、断网和错误返回。
- **验收与效果**：每条旅程记录成功条件、故障恢复、服务器/设备版本与日志；提供商不支持能力显示一致；恢复后进度、用户和媒体身份正确。发现单模块测试无法覆盖的协作缺陷。
- **依赖**：T07 环境预检，专用测试账号/服务器与接收端；不得依赖生产用户数据。

### T04 · P1：建立当前性能基线，按证据优化详情与播放

- **目标与责任**：移动端/媒体负责人找出真实等待与卡顿来源。
- **具体改进**：运行已有 Macrobenchmark 和性能工作流，固定设备、构建、数据集及冷热状态，完整采集启动、首页滚动、详情导航和播放首帧；补充请求阶段、预热释放原因、内存/保留对象与渲染 trace。先验证 F05，确有成本再调整预热身份和起播位置处理。
- **验收与效果**：产出可复现基线与前后对比；报告启动/首帧和帧耗时分布，保留失败场景。根据测量噪声设置相对退化阈值，不承诺未经测量的提速百分比；优化后续播、选版本、跨服切换仍正确。
- **依赖**：T03 固定旅程与可运行基准的设备。指标选择参考 [Macrobenchmark 指标](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)。

### T05 · P1：验证服务可用性、容量与恢复

- **目标与责任**：服务端负责人明确重启与扩容边界，保证可恢复。
- **具体改进**：测试维护排空、服务重启、房主断线和房间重建提示；测连接/消息/账户同步负载、SQLite 锁等待及执行队列、渲染队列上限；在隔离环境执行备份恢复和密钥恢复。若确需多实例或房间跨重启恢复，再设计房间归属、路由及持久状态。
- **验收与效果**：没有静默失房或无限重试；恢复流程有操作手册和实测结果；容量报告给出吞吐、延迟、资源与过载行为。先建立 SLO 和实测容量，再决定存储架构，避免无依据替换数据库。
