## 1. 平板无法播放：片源访问被拒绝，且客户端掩盖了错误类别

当前会话记录 5 次 `transport_range_failed`，均为 `Authorization`、HTTP 403，
读取起点都是 0，未接受到有效 Range 数据。问题发生在打开片源阶段，尚没有成功解码输出的证据。

首轮可核对的链路：

| 时间 | 事件 |
| --- | --- |
| 23:27:45.988 | 平台探测的片源请求返回 403 / Authorization |
| 23:27:51.620 | YCore 本地 HTTP 代理的上游请求返回 403 / Authorization |
| 23:27:51.622 | FFmpeg 打开源失败，却看到 5XX，被归类为 Network / SourceOpen |
| 23:27:52.137 | NativeDirect 打开源失败，归类 Network |
| 23:27:52.140 | 触发 transport_read_recovery |
| 23:27:52.985 | 当前播放以 native_only_failure 结束 |

代码确认：

- `AndroidYCoreHttpProxy.kt:929` 对尚未发出响应的所有服务异常统一返回 502。
- `scripts/native/ycore_demux_jni.cpp:645` 本可以把 FFmpeg 的 401/403 分类为 Authorization；
  上游真实状态在代理层变为 502 后，无法再走该分支。
- `AndroidAdaptiveCore2YPlayer.kt:1386` 按 Network 且可恢复的失败触发同路重开。

整个当前会话共 10 次 `native_direct_failed` 和 3 次 `transport_read_recovery`，
这些是多轮尝试中的事件数，不代表 10 个不同片源或 10 次独立用户点击。

**已确认的客户端缺陷**：至少在增强探测代理链路中，403 被转换为 502，掩盖访问拒绝并进入网络恢复路径。
应保留可识别的 401/403 状态/错误类别，并让鉴权错误明确提示、停止无效网络重试。
这能修复错误分类与体验，但不会自动让服务器接受原本被拒绝的请求。

**仍需外部核对**：媒体 API 可以取得 PlaybackInfo，不代表实际媒体 URL 有访问权限。
需要对照同片源在其他客户端的结果、媒体服务端访问日志，核查登录状态、媒体 URL 有效期、
请求头及访问策略。日志中的主机和凭据已脱敏，不能仅凭这份 ZIP 确定哪一项导致 403，
也不能将片源 403 直接断言为 Cloudflare WAF 拦截。

## 2. 手机慢起播和缓冲：有成功音视频输出，持续数据供应/缓冲恢复仍需复现

这段播放请求成功返回 HTTP 206，使用 HTTPS/h2，无重定向；当前会话没有
`transport_range_failed`、`native_direct_failed` 或 `transport_read_recovery`。
片源是 MKV / HEVC / HDR10，服务端报告码率约 15.17 Mbps。

| 阶段 | 耗时/状态 |
| --- | --- |
| 点击播放至条目准备完成 | 5.429 秒 |
| 平台探测 | 8.004 秒，达到 8 秒期限 |
| 增强探测 | 8.819 秒 |
| 解码器配置探测 | 0.184 秒 |
| 路由选定至首个视频输出 | 约 20.87 秒；现有日志不能细分这段等待 |
| 点击至首个视频输出 | 43.468 秒 |
| 点击至首个音频输出 | 43.676 秒 |

实际视频解码器为 `c2.mtk.hevc.decoder`，视频仍是硬解。路由名 SoftwareFallback
不等于整条视频链路使用软件解码；日志显示增强解复用与 FFmpeg 软件音频，选择了 AAC 音轨。

随后出现 3 次缓冲，累计 25.358 秒，最长 20.629 秒；最后停在约 12.928 秒。
停止前诊断记录压缩队列约 4.58 MB、缓冲时长 969 ms、空队列轮询累计 18 次。
这个计数是队列取样时没有可用样本的次数，不等于 18 次网络断线。

音频曾多次显示 Rendering，累计写入 2,547,712 字节 PCM，音频播放头前进到 620,544 帧。
最后长缓冲阶段 PCM 写入量和播放头都不再增长，AudioTrack 为 paused，underruns=0。
`AndroidEnhancedPlaybackSession.kt:1818` 的输出门控在等待缓冲时调用暂停音频，
与观察吻合，不能据此认定设备完全不支持音频或音频解码器始终失败。
`pcmZeroWrites` 是非阻塞写入无空间/没有进展的统计，也不能单独当成解码失败。

**已确认**：启动时间明显偏长，播放后持续缓冲，声音等待与缓冲停钟相关。
**尚未确认**：网络持续吞吐不足、解复用读取等待、音视频队列阻塞或恢复阈值中的哪一项是根因。
当前导出报告缺少缓冲期间的连续读取耗时、吞吐、每轨队列、输出门控阈值及阻塞状态，
不足以精确归因；不应直接以“加大缓存”或“换解码器”作为已验证修复。

下一步应在同片源复现，记录首帧前各打开/选轨/预缓冲阶段，及停顿期间的读取吞吐、
每轨队列时长、待消费音视频包、缓冲阈值、endOfInput/atCapacity 和门控状态。
再据此判断是服务/网络问题，还是播放器缓冲恢复与调度问题。

手机当前播放 serverref 为 `p114a709d7d1e55334666bcd6`，其媒体 Range 请求成功；
同期 Cloudflare 标记和 Unauthorized 主要对应其他 serverref，不能把它们直接当作这段视频卡顿的原因。

## 深入分析与修复建议

### A. 访问拒绝需要保留到最终错误提示，不能只改一处 HTTP 状态

已确认两层信息丢失：代理统一发出 502；平台/增强探测又把失败统一收敛成
`YCore2ProbeFailure.SourceUnavailable`，路由评估仅保留 Success，否则得到 null。
这把“当前身份无权访问”与“本探测器不能识别容器”混在一起，后者仍可能触发其他路由尝试。

建议优先级 P1：

1. 为探测结果保留 Authorization、NotFound、Timeout、Transport、Unsupported 等可执行类别，
   只对适合更换解复用器/解码器的 Unsupported 或不确定媒体能力尝试其他路由。
2. 对尚未发送响应头的代理请求，以白名单映射返回 401/403/404/410 等真实类别。
   不透传源站 HTML 页面。对于已经发出 200/206 后发生的读取错误，状态行无法再更改，
   应通过代理会话保存类型化上游失败，关联给播放器，而非只关闭连接留下 EOF/Network。
3. 鉴权拒绝停止同 URL 的盲目重试。明确提示重新登录或访问受限；如果怀疑媒体 URL 失效，
   在确有依据时重新获取一次 PlaybackInfo，再验证同片源，避免无限刷新。
4. 在可控环境中对比媒体 API 与实际媒体 URL 的鉴权、User-Agent、Range、重定向及凭据作用域。
   目前无法从脱敏 ZIP 断言是哪项请求头缺失、令牌过期或策略拒绝。

验证应覆盖首次打开 403、401、源中途 403、404、503、超时和取消：
403 最终必须是 Authorization，不能启动网络恢复或解码回退；临时 503/超时仍保持有界恢复，
已发送响应头的中途错误也应显示原始类别。

代码入口：`AndroidYCoreHttpProxy.kt:929`、`AndroidCore2MediaProbe.kt:343` 和 `resolveProbe()`、
`AndroidEnhancedMediaProbe.kt:302`、`AndroidAdaptiveCore2YPlayer.kt:1386`。

### B. 连续缓冲提高恢复门槛，说明了停顿可能被放大，但尚不能证明本次触发原因

`YPlaybackBufferGate` 将恢复阈值乘以连续缺数据次数（最多按 3 次），并设目标缓冲的 75% 上限。
例如仓库现有测试中，目标 8 秒、基础恢复量 2.5 秒，会依次要求 2.5、5、6 秒。
这是代码/测试中的示例，不是该手机会话已记录的实际阈值。

`AndroidEnhancedPlaybackSession.pumpInternal()` 在门控关闭时直接返回，暂不执行喂包、音频排空
及视频排空；`suspendOutputForBuffering()` 同时暂停音频与媒体时钟。因此画面保持最后一帧、声音停止
与当前实现一致。恢复条件依赖压缩队列时长、输入结束或队列满，没有墙钟等待上限。

读取层已有保护：Range 空闲期限按缓冲量取 4–12 秒，单次 Range 包括重试总预算默认 30 秒，
OkHttp 连接/读取超时默认 20 秒。不能称为“完全没有超时”，也不能仅因最长缓冲约 20 秒就断言
触发了 OkHttp 超时；日志在总预算到期前由用户暂停，没有记下最终读取失败。

建议优先级 P1：

1. 先加入缓冲状态的进展记录：当前/目标/恢复时长、各必选轨队列、最后新增压缩包/输出帧时间、
   活跃读取阶段、累计/重试耗时、有效吞吐、队列满/EOS、待消费 codec/PCM 包。
   只记录匿名源身份与数值，不记录凭据。
2. 给播放级缓冲增加“无有效进展”判定，与已有 Range 预算协调；可从 5 秒提示、
   10–15 秒评估一次有界恢复开始做实验，但这不是本次已验证参数。恢复前保留实播位置、暂停意图和选轨。
   区分用户暂停、慢速但持续进展、读取失败和内部队列不推进，避免抢占正常播放或重试风暴。
3. 连续缓冲阈值应有衰减和等待上限；恢复顺畅后逐步回落。评估低延迟恢复的代价，
   不应直接永久降低阈值或无条件放行，也不应简单扩大缓存把等待转移到首帧。
4. 队列时长当前按所有非字幕样本的最早/最晚 PTS 计算，不能保证每条必选轨都有连续可播数据。
   建议记录并评估必选音/视频轨共同可播区间，处理单轨 EOS、时间戳不连续及无音频片源，
   防止一条轨领先掩盖另一条轨缺数据。

验证：稳定吞吐、突发低速、持续少量字节、完全停止读取、音视频包交错不均、满队列可变码率、
音频有包但视频无包、用户暂停/拖动、真正 EOF。验收应检查恢复时间、重复缓冲率和音画同步，
不能只看“画面恢复了一次”。

### C. 读取调度存在一个应单独验证的竞争窗口

静态代码显示一个潜在的补读请求丢失时序：填充线程决定达到高水位并退出后，
消费者可能先取走样本并请求补读，此时 `fillScheduled` 仍为 true，请求被忽略；
随后填充线程在 finally 中仅将它清成 false，不重新检查需求。
若消费后同时进入门控关闭状态，下一轮 pump 不再调用 pollSample，可能缺少新的补读触发。

这只是根据锁和状态更新次序识别的风险，**尚未复现，不能认定为该手机此次停顿根因**。
建议在单元测试中用 barrier 固定上述时序；确认后将“清除填充状态并重新核对需求”放在同一锁内，
或让缓冲等待路径主动确认填充任务仍然存在。修复需同时覆盖 close/seek/generation 变化，避免复活旧任务。

### D. 首帧 43.5 秒应拆分优化，已有 prepared-demux 复用不宜重复实现

已知平台和增强探测串行消耗约 16.8 秒；解码器配置探测仅约 0.184 秒。
路由选定到首帧还占 20.87 秒，这段需要新增打开、选轨、seek、首包、预缓冲、首帧提交/呈现时间点。
不能将这 20.87 秒全部归为解码器配置。

已有 `takePreparedEnhancedDemux()` 和探测结果移交机制。建议先记录缓存/移交是否命中、失效原因、
是否重新 open/seek，以及为何首个 2 MiB 块重复读取；不能仅凭多次读取认定其全部多余。
在有足够轨道/编码信息且不影响 DRM/Dolby 身份校验的条件下，再评估减少平台探测等待、提前采用
已验证的增强路径，并保留未知片源的完整探测回退。避免一律并行打开多个解复用器增加重复请求。

验证：冷/热缓存、单/多音轨 MKV、HDR10/Dolby、慢速源、403 源；分别比较探测耗时、首帧分位数、
首块重复请求数、正确选轨和回退成功率。

推荐顺序：先修复 A 的确定性错误分类；同时为 B/D 补充能区分根因的指标，复现并检查 C；
根据复现结果修改补读调度和缓冲恢复，再优化首帧探测。媒体服务器的权限/访问策略需同步核查，
不能用客户端重试或解码回退替代。
