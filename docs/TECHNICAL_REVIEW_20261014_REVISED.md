## 1. 总体结论与证据边界

项目已具备实际运行的共享模块、版本与模块边界检查、原生解复用源码和构建链路，以及较大规模的自动化测试。原报告将部分维护成本、条件性风险和未测量的性能猜测写成了确定缺陷，并提出了可能破坏兼容性或并发正确性的修改方案，需要纠正。

当前优先处理三个方向：**渲染服务的默认配置与网络出口约束、公开交付包的更新签名策略、版本规则校验的实际缺口**。随后建立播放与服务端性能基线，再实施缓冲区优化和高复杂度模块拆分。仅凭本次证据，不能将模块目录布局、双接口适配或 Git 体积列为 P0 阻断问题。

本次没有进行生产部署检查、真实攻击链验证、设备播放回归或功耗测试，也没有重新打包。生产服务是否采用示例令牌、实际 APK 是否内置更新验签公钥、旧客户端的更新行为及设备上的真实瓶颈，均需另行验证。未确认 P0 不等于已经证明项目不存在严重漏洞。

### 1.1 判定与优先级

| 标记 | 含义 |

## 3. 安全与交付策略

### S1：客户端内置 TMDb 应用令牌——已确认，P2

构建配置将令牌写入 `BuildConfig`；客户端仍需要未登录时的直接 TMDb 路径。已登录代理访问和游客直接访问并存，因此不能简单删除令牌并要求所有请求走账号代理。发布工作流也依赖该构建输入，单改客户端会影响构建或游客功能。

证据：[构建注入](D:/Demo/Yfuse/composeApp/build.gradle.kts:948)、[登录与游客分流](D:/Demo/Yfuse/composeApp/src/commonMain/kotlin/com/yfuse/core/network/Tmdb.kt:43)、[发布输入](D:/Demo/Yfuse/.github/workflows/publish-android.yml:482)。

修订判断：嵌入 APK 的应用凭据可以被提取，存在额度滥用和轮换成本；不能据此认定用户账号凭据已经泄露。本次未检验令牌有效性、权限或滥用情况，不在报告中记录令牌值。

建议先选择受限的匿名代理、用户自备凭据或保留受控应用令牌的产品方案，再同步客户端、服务端和 CI。验收应覆盖游客、已登录、后端关闭、代理不可达、限流及令牌轮换场景。

### S2：允许 HTTP 媒体源——配置已确认，影响取决于实际请求，P2

[网络安全配置](D:/Demo/Yfuse/composeApp/src/androidMain/res/xml/network_security_config.xml:7) 允许基础明文流量，背景包括用户输入的 NAS/Emby/WebDAV 等地址。账号和更新路径另有 HTTPS 与同源限制，不能从这个配置直接推导“账号令牌会明文发送”。但使用 HTTP 的媒体服务凭据和内容确实缺乏传输加密。

将全局默认改成禁止、只给静态域名开白名单，无法完整适配动态 IP、自建域名和同一主机不同端口的用途。原生播放网络实现也不能假定完全受 Android Network Security Config 约束。

建议把官方服务的 HTTPS 要求与用户媒体源策略分别落实：记录用户对 HTTP 源的明确选择，限制凭据跨源和重定向转发，在所有相关网络实现中执行同一策略。验收覆盖局域网 IP、自建域名、同主机异端口、HTTPS 到 HTTP 重定向和跨主机鉴权头处理。

### S3：IP 端点与 TLS pinning——撤回“无 pin 即漏洞”，P3

使用 IP 端点会带来证书与端点迁移维护成本，但“未固定证书”本身不是已确认漏洞。原报告称没有 `default_sni` 也不正确，[Caddy 配置](D:/Demo/Yfuse/watchTogetherServer/deploy/Caddyfile:4) 已设置该项。

应先验证证书链、主机名、续期与客户端端点迁移。Android 官方一般不建议应用使用证书固定；若特定威胁模型要求固定，需要备用密钥、轮换和失效恢复设计，不能把强制 pin 作为通用修复。[Android TLS 安全指南](https://developer.android.com/privacy-and-security/security-ssl)

验收关注续期和证书链变化时的真实连接行为；TLS pinning 与更新清单 Ed25519 验签是不同机制，不应相互替代。

### S4：公开交付包的更新验签要求——策略缺口，P1

仓库公钥属性为空，不代表最终发布 APK 一定没有公钥：Gradle 和 CI 支持注入，并已有生产签名及发布清单相关检查。另一方面，`packageOnly` 和部分本地构建路径允许缺少公钥，公开交付的准入规则需要更明确。

证据：[构建期检查](D:/Demo/Yfuse/composeApp/build.gradle.kts:1106)、[CI 公钥与发布策略](D:/Demo/Yfuse/.github/workflows/publish-android.yml:295)、[更新验证实现](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/update/AppUpdateManager.kt)。

即使清单没有可信公钥，安装前仍有 APK 大小、SHA-256、包名、版本和签名证书等检查；原报告不能省略这些已有保障。清单签名提供的保护也不能由这些检查完全替代。

建议区分公开交付与明确标识的诊断产物，对公开交付包强制验证公钥、签名清单和实际 APK 的一致性；密钥轮换须兼顾存量客户端。验收加入缺失密钥、错误密钥、被篡改清单和旧密钥迁移案例。需读取实际交付包配置，才能判定既有版本的具体风险。

### S5：HTTP 历史更新入口——已确认入口，旧版影响待验证，P2

[Caddy 配置](D:/Demo/Yfuse/watchTogetherServer/deploy/Caddyfile) 保留历史 HTTP 更新兼容路径，并对账号和观看服务作了更严格处理。当前更新客户端的保护不能证明所有旧版本都安全，也不能反向证明旧版已经可被利用。

先列出旧客户端版本、所用清单、下载 URL、验签与升级能力，再决定退役 HTTP 路径。单纯增加 301 无法保护第一次 HTTP 请求，且贸然关闭入口可能切断旧版升级。验收应覆盖受支持旧版到新版的完整升级链，并确认凭据接口不能借兼容入口降级到 HTTP。

### S6：解复用 JNI 源码缺失——撤回；改为产物追溯核验，P3

主要实现存在于 [ycore_demux_jni.cpp](D:/Demo/Yfuse/scripts/native/ycore_demux_jni.cpp)，共 3,873 行。[解复用构建脚本](D:/Demo/Yfuse/scripts/build-ycore-demux.sh) 已包括固定 FFmpeg 提交、源码编译、校验和及来源记录；[原生构建入口](D:/Demo/Yfuse/scripts/build-ycore-native.sh:17) 和 [原生构建工作流](D:/Demo/Yfuse/.github/workflows/build-yfuse-mpv-dolby.yml) 也存在。

因此“无法审计、无法构建、无法响应原生漏洞”的结论不成立。仍应核对交付库与源码提交、工具链和来源记录是否对应；存在构建脚本不等于本次已经验证了逐字节可复现构建。验收是从固定输入构建并核对产物记录，必要时另外执行可复现性实验。

### S7：代理头信任与容器监听——部署相关，撤回已证实绕过，P2

[WatchTransport](D:/Demo/Yfuse/watchTogetherServer/src/main/kotlin/com/yfuse/watch/WatchTransport.kt:18) 限定了代理头的信任条件，非 loopback 对端不会仅凭转发头获得同样信任；[既有测试](D:/Demo/Yfuse/watchTogetherServer/src/test/kotlin/com/yfuse/watch/WatchTogetherServerTest.kt:2020) 覆盖非 loopback 伪造头。容器监听 `0.0.0.0` 和声明 `EXPOSE`，不足以证明公网可伪造代理身份。

应核实实际端口发布、反向代理位置、服务端看到的 socket 对端，以及是否存在改变来源语义的插件。把容器内部监听一律改为 loopback，可能使桥接网络中的代理无法连接。

可根据拓扑采用宿主机 loopback 端口发布或私有容器网络，并与应用信任策略配套测试。Docker 官方说明了发布端口绑定宿主机 loopback 的行为；这与容器内部绑定 loopback 是两件不同的事。[Docker 端口发布说明](https://docs.docker.com/engine/network/port-publishing/)

验收须同时证明合法代理可用、外部直连不可绕过、伪造转发头无效。健康检查可独立补齐，但它不是代理信任漏洞的修复措施。

## 4. 架构与模块边界

### A1：共享模块——撤回“虚拟模块”；保留布局改进，P2

[phoneShared](D:/Demo/Yfuse/phoneShared/build.gradle.kts) 与 [tvShared](D:/Demo/Yfuse/tvShared/build.gradle.kts) 是实际 KMP/Android 编译模块，通过 source set 引用其他目录。源码不位于模块目录内部，不等于模块没有编译或依赖边界。两个模块处于不同 APK 的依赖图，同 namespace 也不能直接推导 DEX 冲突。

[模块边界脚本](D:/Demo/Yfuse/scripts/verify-module-boundaries.py) 已进入 CI，但其检查范围不等于完整架构约束。可以逐步把公共源码放到清晰的归属目录，补依赖方向检查；迁移前后比较两端编译输入、产物和构建时间。原报告“近两倍构建成本”的数字没有测量支持。

### A2、A3：双接口与 `core` / `core2`——改写为迁移复杂度，P2

`core` 包含账号、网络、数据与模型等基础能力，不能仅凭目录名把它认定为另一套完整播放内核。产品级播放选择与内核内部解码、渲染路由也有不同职责，需要按调用链识别重复。

[LegacyYPlayerAdapter](D:/Demo/Yfuse/composeApp/src/commonMain/kotlin/com/yfuse/core2/legacy/LegacyYPlayerAdapter.kt:33) 使用映射状态；[YPlayerVideoEngineAdapter](D:/Demo/Yfuse/composeApp/src/commonMain/kotlin/com/yfuse/core2/legacy/YPlayerVideoEngineAdapter.kt:131) 在可识别的适配路径复用原状态。这些证据不支持直接认定存在两个独立可写的状态真相或已经发生有损转换。

迁移与退役条件也已存在于 [YCore2 架构文档](D:/Demo/Yfuse/docs/YCORE2_ARCHITECTURE.md) 和 [Native readiness 定义](D:/Demo/Yfuse/composeApp/src/commonMain/kotlin/com/yfuse/core2/release/YCoreNativeReadiness.kt:131)，但其中未测量项不能当作已经通过。

建议建立接口能力矩阵与映射测试，覆盖播放、轨道、字幕、错误、seek、恢复和释放，逐项收敛真正重复的职责。旧接口或兼容内核的删除必须满足现有素材、设备与稳定性门槛；不能以统一接口为由提前移除 MDK 或已承诺能力。

### A4、A8：高复杂度播放与详情编排——已确认维护成本，P2

Direct、Adaptive、Enhanced 和 HTTP 代理文件分别约 3,428、3,297、2,683、2,347 行，值得优先审视。[函数长度基线](D:/Demo/Yfuse/config/function-size-baseline.txt) 可定位大函数，但行数不能单独证明具体故障。

拆分以资源和状态所有权为边界：播放命令与状态迁移、解复用读取、音频输出、视频释放、seek 和收尾；详情侧可分目录加载、媒体源解析和播放准备。先固定可观察行为，再移动实现，每批缩减对应函数基线。不要仅把长函数搬到工具文件，形成跨文件共享可变状态。

验收重点是事件顺序、旧任务取消、连续 seek、切源、错误恢复及资源仅释放一次；详情加载应保留“最新请求生效”的行为。

### A5、A6、A7、A9：依赖与状态管理——撤回框架用法即缺陷的判断，P2/P3

| 条目 | 修订判断 | 合理改进与验收 |
|---|---|---|

## 5. 播放性能：确认机制，测量收益

### PERF-1、PERF-2、PERF-4：数据复制与直接缓冲区分配——已确认路径，收益待测量，P2

[AndroidFfmpegDemuxer](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/core2/android/AndroidFfmpegDemuxer.kt:165) 已复用直接缓冲区 `packetStorage`，随后复制为具有独立生命周期的数据包。[预读队列](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/core2/android/AndroidDemuxReadAheadNode.kt:25) 会让多个数据包同时存活，因此该复制承担了所有权隔离职责。

[音频输出](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/core2/android/AndroidNativeDirectYPlayer.kt:2627) 存在 `allocateDirect`；非阻塞写入未消费完成时会保留待写数据。[Cronet 读取](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/core2/android/AndroidCronetMediaTransport.kt:143) 则在复制后将数据排队，随后复用网络缓冲区继续读。

原报告建议的“单个缓冲区复用”或直接 `slice()` 不足以保证这些路径正确：下游尚未消费完的数据可能被下一次读取覆盖。直接缓冲区分配、堆对象分配和真实 GC/卡顿之间也需要测量，不能仅凭代码推导抖动幅度或每秒数据块数。

建议先记录分配字节、队列峰值、写入未完成次数、GC 与音频 underrun；确认瓶颈后再设计有界缓冲池。每个缓冲区必须有唯一持有者或明确租约，在消费完成、异常、seek、取消、切源和关闭时归还，并保留背压。验收覆盖消费者落后、部分写入、连续 seek、取消和内存压力，检查数据内容与播放输出，不能只比较速度。

### PERF-3：固定 2 ms 轮询——撤回，改为实际唤醒测量，P3

[AndroidPlaybackTiming](D:/Demo/Yfuse/composeApp/src/androidMain/kotlin/com/yfuse/core2/android/AndroidPlaybackTiming.kt:47) 已按状态决定等待时间：预览请求为 2 ms，非播放分支为 250 ms，缓冲为 10 ms，按视频释放时间的分支为 2～10 ms，默认播放分支为 8 ms。调用方还结合唤醒信号和是否允许泵送进行等待。

因此，遗留的 `PUMP_IDLE_DELAY_MS = 2L` 常量不能证明运行路径持续每秒唤醒 500 次，也不能把辅助函数的 250 ms 分支等同于所有暂停状态固定轮询。可以删除确认未使用的常量，并测量播放、暂停、缓冲和预览的实际唤醒与能耗，再决定是否调整调度。
